# Coding Agent 只读顾问：模块与部署架构

> 状态：模块边界修订版，2026-10-12  
> 首个试点：Planora「技术规格书语气改写」  
> 范围：只读顾问、页面接入、代码/运行材料读取、外部会话和查询笔记；不做自动改代码和发布。

## 1. 先区分四种概念

| 名称 | 在本系统中的含义 | 例子 |
|---|---|---|
| **职责面** | 按数据流或控制流划分的一组稳定责任；不等于进程或服务 | 交互、编排、证据访问、推理、记录 |
| **模块** | 可以独立替换、部署或定义接口的一组功能 | Page Connector、Runner、Code Access |
| **组件** | 模块内部的具体实现 | `onSave(batch)`、`buildPrompt`、`RuntimeReader` |
| **工作流** | 多个模块串起来完成的一次业务动作 | 提问、追问、生成研发建议 |

因此：

- DSH 是 **推理模块里的外部执行器适配组件**，不是一层；
- 证据检查是 **Runner 编排模块中的确定性校验组件**，不是一层；
- 回答组织是 **Runner 的输出组件**，不是独立服务层；
- “提案与研发确认”是 **可选工作流模块**，依赖会话记录，不是基础层。

## 2. 五个职责面

```text
┌─────────────────────────────────────────────┐
│ 交互面：页面入口                             │
│ Page Connector / PinAsk                      │
└──────────────────────┬──────────────────────┘
                       │ 页面事实 + 问题
                       ▼
┌─────────────────────────────────────────────┐
│ 编排面：一次顾问会话                          │
│ Runner / Orchestrator                        │
│ 绑定项目环境、安排读取、检查证据、组织回答      │
└─────────────┬───────────────┬───────────────┘
              │               │
              ▼               ▼
┌─────────────────────┐ ┌─────────────────────┐
│ 证据访问面           │ │ 推理面              │
│ Code Access          │ │ DSH Adapter         │
│ Runtime Access       │ │ Context Notes       │
│ Generic Tools        │ │                     │
└──────────┬──────────┘ └──────────┬──────────┘
           │                       │
           └───────────┬───────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ 记录面：外部 Advisor Workspace                │
│ 会话、证据、查询笔记、确认事实、研发决定       │
└─────────────────────────────────────────────┘

横切控制：只读权限、命令白名单、版本/环境绑定、证据一致性规则。
可选工作流：生成待研发确认的修改建议 → 研发记录决定。
```

这五个职责面是系统结构；它们不要求对应五个进程。Planora P0 可以由一个本地 Runner 进程调用现有 DSH 和文件系统完成。

## 3. 模块清单

### 3.1 交互模块：Page Connector

| 项目 | 内容 |
|---|---|
| 输入 | 页面点选、URL、可见文本、祖先结构、时间、专家问题 |
| 输出 | `page_context`，提交到 Runner |
| 当前实现 | `[已实现]` PinAsk overlay；有 `onSave(batch)` 接入点，截图仍为 `not-captured`（`/Users/ltc/CursorProject/中交机电局项目/pinask/overlay/pinask.js:338,456`） |
| 不负责 | UI 到源码映射、运行 ID 猜测、SSH/数据库/模型凭据 |
| 后续 | 页面长期无法定位运行时，才增加页面适配器 |

### 3.2 编排模块：Advisor Runner

Runner 是把各模块接起来的薄进程，不是业务 App 的插件，也不是项目方需要修改的代码库模块。

| 内部组件 | 作用 |
|---|---|
| Request Receiver | 接收 PinAsk 或 JSON 请求 |
| Project Binding | 绑定项目、环境和外部工作区；不从页面猜 `project`/`environment` |
| Session Controller | 创建会话、处理追问、加载历史 |
| Access Planner | 决定先查代码、运行材料还是页面已有线索 |
| Evidence Checker | 检查路径、版本、环境和运行候选是否冲突 |
| Answer Composer | 把 DSH 输出整理成结论、证据、推导和缺失材料 |
| Response Writer | 把回答和追问结果返回给 PinAsk/CLI |
| Workspace Writer | 保存会话、证据和查询笔记 |

当前状态：`readonly-advisor` CLI 已实现会话、追问、提案和研发决定；`runner/server.js` 提供本机 HTTP，可接 PinAsk batch 与 `/ask`。

### 3.3 证据访问模块：Evidence Access

这是一个模块，内部包含两种不同的读取器：

| 组件 | 读取内容 | 首轮入口 |
|---|---|---|
| Code Access | 源码、配置、目录、Git 版本 | Planora 本地目录或 Git 只读 |
| Runtime Access | 日志、结果、中间产物、运行记录 | Planora 固定导出目录；之后可用 SSH/只读命令 |

两者都只读。没有运行材料时，只能解释实现，不能声称还原某次实际运行。

### 3.4 工具执行模块：Generic Tool Executor

这是证据访问模块使用的工具执行组件，不是项目方要维护的工具集合。

| 工具职责 | 示例 | 状态 |
|---|---|---|
| 目录和文件 | 列目录、读文本 | P0，优先复用 DSH |
| 搜索 | 受限文本搜索、关键词搜索 | P0，优先复用 DSH |
| 版本事实 | Git commit、分支、工作区状态 | P0 |
| 运行搜索 | 按时间、现象、关键词查材料 | P0/P1，取决于导出材料 |
| 结构检索 | LSP、调用图、外部代码索引 | P1/P2，失败信号触发 |

工具权限由执行环境限制，不能只靠提示词要求 Agent 不写文件。

### 3.5 推理模块：DSH Adapter 与 Context Notes

推理模块包含两个组件：

| 组件 | 作用 | 状态 |
|---|---|---|
| DSH Adapter | 把当前问题、证据和必要上下文交给 DSH，接收分析结果 | `[已实现]` CLI 调用 DSH headless |
| Context Notes | 在外部工作区保存少量代码地图、任务入口和运行读取笔记 | P0 轻量计划 |

Context Notes 不是项目知识库，也不是完整业务模型。首问没有笔记时必须仍能工作；笔记生成失败时退回通用搜索。

Flash/Pro 是 DSH Adapter 的模型调用策略，不是两个系统模块：

- P0：Flash 作为配置目标，Pro 由人触发；
- 后续：有确定性检查器和实验数据后，再考虑自动升级。

### 3.6 记录模块：Advisor Workspace

外部工作区由顾问管理，目标代码库不写入这些内容：

```text
<advisor-data>/<project>/<environment>/
  project.json
  notes/
    map.md
    task.md
    runtime-reading.md
  sessions/<session-id>/
  confirmed-facts.jsonl
```

它保存：

- 问题、回答和追问；
- 实际读取的文件、符号、运行材料和版本；
- 顾问生成的查询笔记；
- 专家或研发确认过的事实和决定。

`observed`、`derived`、`confirmed` 和 `stale` 是记录状态，不是四个模块。

### 3.7 可选工作流：研发建议与确认

这不是基础“回答问题”链路，而是会话记录之上的可选工作流：

```text
专家会话
  → 顾问生成待研发确认的修改建议
  → 研发批准、拒绝或要求补充
  → 决定写入会话记录
```

当前 CLI 已有 `propose` 和 `review` 命令，但它们不会修改、提交或发布代码。自动修改和自动验证不属于当前顾问产品范围。

## 4. Runner 应该放在哪里

Runner 的位置由两个条件决定：

1. 它能否访问代码只读入口；
2. 它能否访问运行材料只读入口。

它不需要与业务 App、数据库或生产服务同机。

### 4.1 Planora P0 推荐

```text
Mac 浏览器中的 PinAsk
          │ localhost 请求
          ▼
Mac 本地 Runner
  ├─ Planora 本地代码副本（只读）
  ├─ Planora 运行导出目录（只读）
  ├─ DSH headless
  └─ 外部 Advisor Workspace
```

Planora 由我们自己启动 Runner。项目方不需要先安装或维护 Runner。

### 4.2 三种部署位置

| 位置 | 好处 | 代价 | 适用情况 |
|---|---|---|---|
| 我们的 Mac/中台 | 开发和调试简单，平台统一管理 | 需要项目提供代码/运行材料访问；网络和凭据处理更复杂 | Planora P0、允许材料出项目网络 |
| 项目方网络内的独立 Runner | 访问内网日志和 SSH 简单，凭据不出项目侧 | 项目方要启动、升级和监控一个进程 | 运行材料不能出域，或测试环境只允许内网访问 |
| 业务服务同机 | 可直接访问本地文件和端口 | 把顾问和业务服务绑死，权限和故障影响面更大 | 默认不采用，仅特殊网络限制时考虑 |

推荐顺序：Planora 先本地；第二个项目再根据网络约束决定是否提供项目侧 Runner 包。项目侧 Runner 是部署选项，不是业务代码契约。

## 5. 谁管理什么

### 平台管理

- PinAsk 连接和回答入口；
- Runner、会话编排和通用工具；
- DSH 调用、Flash/Pro 策略；
- 证据检查规则；
- 外部查询笔记和会话格式；
- 只读访问的执行限制；
- 统一的日志、诊断和版本记录。

### 项目方提供或管理

- 代码只读入口；
- 测试/线上运行材料只读入口；
- 网络白名单、账号或 SSH 凭据；
- 项目和环境名称；
- 已有的运行查询命令或导出方式（有则提供）；
- 能判断回答是否有用的人。

项目方不需要管理：

- `docs/advisor/`、`AGENTS.md` 或 Agent skill；
- 顾问生成的代码地图和任务笔记；
- DSH 提示词；
- 顾问会话数据库；
- UI 到源码的映射逻辑。

## 6. P0/P1/P2

| 阶段 | 需要完成 |
|---|---|
| P0 | PinAsk 页面端到端、薄 Runner、Planora 代码/运行只读、DSH、外部会话、最小查询笔记、证据和追问 |
| P1 | Planora 测试环境访问、可复用 RuntimeReader、确认事实、同题对比实验 |
| P2 | 结构索引、自动技能草稿、页面适配器、Runtime Adapter、项目名录、跨项目和主动刷新 |

## 7. 明确不做

- 不把 DSH、证据检查、回答组织拆成互相独立的服务；
- 不要求业务 App 同机部署 Runner；
- 不把项目方维护导航文件作为接入条件；
- 不把顾问笔记当成项目正式文档；
- 不自动改代码、提交、发布或替专家判断业务质量。
