# Coding Agent 只读顾问：产品定位与交付形态

> 状态：讨论落稿，2026-10-10
> 首个试点：Planora「技术规格书语气改写」
> 当前实现基础：DSH headless，只读工作区，Flash 默认、Pro 按需复核

当前最小可用封装见 [`readonly-advisor/README.md`](</Users/ltc/WindowsProject/wps-addin-poc/readonly-advisor/README.md>)：初始化项目配置、记录专家会话、继续追问，并生成待研发确认的修改建议。

## 1. 当前定位

### 产品能力

本产品提供一层**项目只读顾问能力**：专家、测试或研发人员提出问题，coding agent 读取项目代码、配置、运行材料和日志，返回可核对的证据、解释和证据缺口。

当前阶段只承诺：

- 读取项目材料；
- 按问题定位相关实现和运行证据；
- 区分直接事实、代码推测和缺失材料；
- 在 Flash 结果出现可核对冲突或证据不足时进行 Pro 复核。

当前阶段不承诺：

- 自动修改业务代码；
- 自动部署或发布；
- 要求项目先建立完整白盒化契约；
- 仅凭代码还原一次没有运行记录的线上任务。

### 产品形态和部署形态分开

“只读顾问层”是产品定位；本地工具、项目接入器和中心化服务是不同的交付形态。

第一阶段采用可在本地、项目方可控环境或中台运行的 DSH 顾问实例。项目方必须同时提供代码只读入口和测试/线上服务器运行材料只读入口，才能回答具体某次运行的问题；只有代码入口时只能降级为实现解释。顾问配置、自动生成的地图、任务 dossier 和会话保存在目标代码库之外。多个项目共享权限、会话、审计或检索时，再考虑中心化目录，但不把项目代码和服务器凭据集中托管。

## 2. 最小结构

```text
专家 / 测试人员
        │
        ▼
DSH CLI 或 Web
        │
        ▼
只读顾问配置
（问题模板、Flash/Pro 路由、结果检查）
        │
        ▼
项目只读接入
（代码本地目录/SSH + 服务器只读入口）
        │
        ├── 代码和配置
        ├── 测试/线上运行记录和日志（只读）
        └── 任务产物
```

### DSH 侧

DSH profile/plugin 负责：

- 只读权限；
- 问题模板；
- Flash/Pro 调用；
- 技术门禁和问题覆盖检查；
- 保存问题、回答、读取路径和证据缺口。

### 项目侧

项目侧只需要提供：

- 项目代码的只读入口；
- 只读权限；
- 运行材料的只读入口：导出目录、只读命令、SSH 或已有 API 至少一种；
- 任务名称和一个问题线索；
- 测试或线上服务器的只读 SSH、日志查询命令或只读接口。

项目不必接入完整 DSH，也不必先改造成统一架构。

## 3. 项目级记忆与代码检索层

第一阶段的项目级记忆由顾问在外部工作区生成，不建设独立知识库。项目已有的短配置或说明文件只是可选输入：

- 项目和目标任务；
- 重要代码、配置、产物和日志目录；
- 项目术语；
- 已知证据边界；
- 可选的只读查询命令；
- 可选的外部代码检索命令（本地索引或已有 Sourcegraph），见 [`CODING_AGENT_CODEBASE_MEMORY_LANDING.md`](./CODING_AGENT_CODEBASE_MEMORY_LANDING.md)。

项目记忆不是源代码的替代品，也不是强制开发契约。顾问优先使用 DSH 自带搜索生成外部代码地图和任务 dossier；现成索引 / Sourcegraph MCP 只在失败信号出现后接入。不自研向量平台，也不把白盒化契约当作接入前提。

## 4. 三种交付形态

| 形态 | 适用阶段 | 项目方投入 | 当前判断 |
|---|---|---|---|
| 项目侧 DSH CLI/Web | 单项目试验、专家临时核查 | 提供代码和服务器只读入口 | 当前首选 |
| 项目只读接入器 | 需要查远程日志、运行结果或内部服务 | 提供少量只读命令或接口 | 下一步按实际缺口增加 |
| 中心化服务 | 多项目共用、统一权限和审计 | 配置服务账号、项目连接器和权限 | 暂不提前建设 |

浏览器插件只解决界面入口，不能解决代码、日志、权限和运行材料的读取，因此不作为核心产品形态。DSH Web 已可作为浏览器入口。

## 5. 当前接入条件

### 必须提供

- 可登录的本地目录、容器或 SSH 环境；
- 项目代码、配置、运行材料和日志的实际只读权限；
- 任务名称；
- 一个真实问题或现象；
- 能判断回答是否有用的人。

### 暂时不要求

- 统一任务 ID 或结果引用协议；
- 函数级代码白名单；
- 完整架构图或白盒化契约；
- 专门 MCP 资源；
- 前端改造；
- 自动修改和发布链路。

## 6. 后续扩展顺序

1. **查和解释**：读取代码、日志、运行产物，定位证据和证据缺口。
2. **反馈整理**：生成问题、证据、影响范围和待确认项，减少专家与研发之间的往返。
3. **运行核对**：接入任务 ID、运行记录、版本和审计导出，支持跨版本比较。
4. **修改验证**：在开发模式中提出修改、运行测试并交给专家确认。
5. **审批发布**：在积累足够实践后再考虑自动审批、提交和发布。

第 4、5 步才会重新遇到白盒化契约问题，当前不把它作为接入前提。

## 7. 当前未知项

- 项目方是否愿意把测试环境的只读 SSH 权限交给中台；
- 项目方自有 coding agent 是否已经能完成同样的只读检索；
- 只提供账号、SSH 配置和项目记忆，能否覆盖大多数首轮问题；
- 项目方是否需要统一的会话保存、审计和跨项目检索；
- 中台提供的顾问层相对于项目方自行配置 coding agent 的增量收益。

这些问题需要通过 Planora 的真实专家问题和后续项目接入实验确认。
