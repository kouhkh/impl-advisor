# coding agent 只读顾问接入指南（实验版）

> 状态：实验版，2026-10-10  
> 适用范围：让专家通过 coding agent 读取项目代码、配置、运行材料和日志，获得证据和解释。  
> 当前实现：DSH headless；Flash 默认，Pro 按需复核。首个具体试点是 Planora 的“技术规格书语气改写”。  
> 本指南不是完整白盒化契约，也不要求项目先改造成统一架构。顾问配置、地图、任务资料和会话默认保存在目标代码库之外。

## 1. 先判断是否适合接入

适合首轮试点的项目需要：

- 有正在交付的业务任务和真实问题；
- 有项目代码、配置或运行材料可以只读访问；
- 至少有一名专家、测试或研发人员能够判断回答是否有用；
- 项目方接受第一阶段只提供证据和解释，不自动改代码。

如果项目没有可读的运行记录，只读顾问可以降级查代码和配置，但不能声称还原某次运行；面向专家的正式接入默认要求代码和服务器两类只读入口。

## 2. 项目方最小投入

### 必须提供

1. 可读取的代码目录、容器或 Git/SSH 入口；
2. 测试/线上服务器的运行材料只读入口：导出目录、只读查询命令、SSH 或已有只读 API 至少一种；
3. 代码、配置、运行材料和日志的实际只读权限；
4. 一个真实问题，最好带任务名、运行名、日期、文件名或现象。

### 可以暂时不提供

- 统一任务 ID 或结果引用字段；
- 函数级代码白名单；
- 完整架构图或白盒化契约；
- 专门的日志 API、MCP 资源、页面适配器或项目内顾问文件；已有 SSH、导出目录或只读命令可作为第一接入方式，但没有 `run_id` 时必须能按线索搜索或浏览材料。

如果 Agent 连续两三次找不到同一类材料，再补项目记忆、查询命令或只读适配器。

## 3. DSH 启动方式

使用 DSH 构建后的 CLI，保持工作区是目标项目：

```bash
cd /path/to/project
DSH_HOME=/path/to/dsh-home \
node /path/to/deepseek-harness/apps/cli/lib/bin.js \
  --profile headless \
  "<专家问题>"
```

DSH 的权限配置必须是只读。凭据由运行环境提供，不能写进问题、报告或项目仓库。当前本机验证过的目标项目是 `wps-addin-poc` 和 Planora；线上项目、SSH 和远程日志尚未验证。

Planora 的专项结果见 [`DSH_PLANORA_READONLY_EXPERIMENT_20261010.md`](</Users/ltc/WindowsProject/wps-addin-poc/docs/DSH_PLANORA_READONLY_EXPERIMENT_20261010.md>)。当前接入仍以静态代码和已落盘产物为主，尚未接入具体线上 `AiJob` 或 `ReviewSession`。

### 3.1 面向项目方的最小封装

仓库中的 `readonly-advisor/cli.js` 对 DSH 做了一层薄封装。项目方只需要初始化一次配置，后续由专家直接提问：

```bash
node readonly-advisor/cli.js init \
  --project planora \
  --task "技术规格书语气改写" \
  --workspace /path/to/planora \
  --output /path/to/advisor-data/planora.advisor.json

node readonly-advisor/cli.js ask \
  --config /path/to/planora.advisor.json \
  --question "为什么这句话被改写？请定位规则、路由或模型，并列出证据。"
```

封装会自动记录问题、回答、工作区提交、只读状态和完整对话过程。专家可以继续追问：

```bash
node readonly-advisor/cli.js followup \
  --session /path/to/session \
  --question "还缺少哪些运行材料？"
```

专家确认问题值得进入研发后，再生成待研发确认的建议：

```bash
node readonly-advisor/cli.js propose \
  --session /path/to/session
```

`propose` 只生成 `change-proposal.md`，不会修改代码、提交或部署。建议中必须包含证据、可能涉及的实现对象、修改边界、验证方式和待研发确认项。

研发确认后记录决定：

```bash
node readonly-advisor/cli.js review \
  --session /path/to/session \
  --decision approved \
  --reviewer "研发姓名" \
  --note "同意先补充 routePolicyVersion，再补回归测试。"
```

`--decision` 可取 `approved`、`rejected` 或 `needs_changes`，决定会写入 `review.json` 并追加到会话记录。

如果项目已有任务说明、质量标准、示例或术语文件，可以在外部配置中列出 `taskContextPaths`。这些是可选输入，不要求项目方新建 `docs/advisor/` 或维护项目专用提示词。顾问仍需根据代码和运行材料生成自己的外部观察和问题 dossier。

如果项目方已有本地代码索引或 Sourcegraph，可在配置中增加可选 `retrieval.commands`，把现成检索层交给顾问调用。默认仍只需 DSH 自带搜索。选型与落地顺序见 [`CODING_AGENT_CODEBASE_MEMORY_LANDING.md`](./CODING_AGENT_CODEBASE_MEMORY_LANDING.md)。

## 4. 给 Agent 的问题怎么写

问题至少说明四件事：

```text
这是一次只读核查。
项目工作区：<项目根目录>
问题线索：<任务、运行、文件、日期或现象>
要求：列出实际读取的文件；区分直接读到的事实、代码推测和仍缺少的事实；不要修改、部署、提交或输出凭据。
```

没有运行编号时，可以先给自然语言现象，让 Agent 搜索；但评估时必须记录它最终实际读了哪些文件。

## 5. 回答的最低验收标准

一个回答只有同时满足下面五项，才算通过第一轮只读顾问验收：

1. **问题覆盖**：回答了本题明确要求的每一项，而不是只给项目概览；
2. **证据存在**：列出的路径真实存在，关键数字和字段能在文件中复核；
3. **事实分层**：明确区分直接读到的事实、根据代码作出的推测、尚缺的运行材料；
4. **关联正确**：没有把不同日期、不同 session 或不同版本的材料混成一次运行；
5. **只读安全**：没有修改、部署、提交、写业务数据或输出凭据。

“回答很长”“使用了更多术语”不算通过标准。

## 6. Flash → Pro 的可落地流程

### 6.1 当前已验证的流程

```text
同一个问题
  → DSH Flash
  → 操作者检查结果
  → 必要时用同一问题和同一材料跑 Pro
  → 人核对两份回答引用的证据
```

这已经可以作为实验流程，但目前的“必要时”由实验操作者人工判断，不能称为自动路由。

### 6.2 未来自动化时由谁判断

自动升级应该由 DSH 外层编排器中的 **结果检查器** 判断，不由 Flash 自评。检查器分三层：

| 检查层 | 检查者 | 可自动检查的内容 |
|---|---|---|
| 技术门禁 | 编排器脚本 | 进程成功、只读权限、必需章节存在、引用路径存在、没有写入动作 |
| 问题覆盖 | 编排器脚本 + 每题的检查清单 | 本题要求的文件、字段、数量、关系是否都被回答 |
| 语义可用性 | 专家或问题负责人 | 解释是否能支持判断，是否足以提出具体反馈 |

只要技术门禁或问题覆盖失败，就把同一问题升级给 Pro。语义可用性由专家判定；专家认为 Flash 证据不足，也可以手动触发 Pro。

### 6.3 升级后的判定

Pro 的回答不能自动覆盖 Flash。两份回答都必须回到实际文件核对：

- 如果 Pro 找到 Flash 漏掉的直接证据，记录为 Flash 漏检；
- 如果 Pro 只是写得更长但没有新增可核验证据，不算收益；
- 如果两者冲突，标记为版本或材料冲突，交给项目负责人确认。

## 7. 一次接入的交付物

首轮只保存以下材料：

- 项目名称、工作区和只读权限说明；
- 专家问题原文；
- 使用的模型和耗时；
- Agent 实际读取的文件路径；
- 直接事实、推测、证据缺口；
- 是否触发 Pro，以及触发原因；
- 专家是否认为回答足以提出反馈。

不要把一次回答直接写成正式任务契约。只有多次实验都出现同一类查找困难，才考虑增加项目记忆、查询工具或适配器。

## 8. 当前状态和下一步

已验证：

- DSH Flash 和 Pro 可以在同一只读工作区完成静态检查；
- Flash 可以从仓库概览和具体运行线索中找到证据；
- 具体线索能暴露运行记录之间的关联缺口。

待验证：

- Planora、ConstructionBot 的真实专家问题；
- 线上 SSH 和远程运行材料；
- 自动结果检查器；
- 专家是否因此减少找 FDE、索要截图和重复解释的时间。
